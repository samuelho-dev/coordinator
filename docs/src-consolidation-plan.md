## 1. Decision and boundaries

The implemented **flat deep-owner layout** consolidates the original22 handwritten +5 generated = **27 files** into **13 handwritten +5 generated =18 files**: ten root owners and three agent modules, nine fewer source files. The previous20 handwritten/25 total selection is **superseded**. Named callable seams remain; redundant physical files and Context plumbing do not.

| Design considered | Result | Decision |
| --- | --- | --- |
| Previous shallow consolidation | 20 handwritten + 5 generated; protected Journal/six-agent-file seams and a new github.ts | Superseded: durability, independent scopes and direct tests do not require separate modules; current artifact names are movable application contracts. |
| Deep existing owners | **13 handwritten + 5 generated =18**; database merge, broker dispatch/GitHub colocation, Plugin journal/status colocation, complete SDK/isolated-entrypoint colocation, six→three agent modules | **Selected**: removes nine files without deleting callable behavior, generated authority, catalog entries or either actual extension entrypoint. |
| More files or generic owner framework | Role directories, new services, wrappers, barrels or scope managers | Reject: not needed by the observed dependency graph or Effect4.0.3. File count is a design judgment, not an Effect mandate. |

Physical consolidation is distinct from the **semantic native-session cutover**. Moving bootstrap code fixes dependency direction; it does not turn a private SDK session into the human's conversation. Target file count does not imply that future integration capabilities are ready.

Do not add RexService, HermesService, RuntimeManager, generic lock engine, another task board, one service per command, provider facades or compatibility barrels. Retain true Effect success/error/requirement channels, generated DB authority, native approvals, consent, isolation and uncertain-delivery fences. Already-acquired layers under their actual owner scopes must not be hoisted merely to make composition look uniform: Plugin's configured MCP owner, optional snapshot store, runner's acquired server and offline recovery ownership have different lifetimes (`src/plugin.ts:26-46`, `src/broker.ts:101`, `src/runner.ts:616-644`, `src/backup.ts:435-448,515-694`). No automatic merge/deploy/activation is proposed.

## 6. Future method surface at existing owners

The following are **proposed capabilities, not existing methods or ready hooks**. They do not count toward today's75 root/program names or9 private handlers. Exact wire names, inputs and admission semantics require implementation approval after host evidence; no new files/services are prescribed.

Proposed action surface for approval (working identifiers, **not source exports**): ordinary Plugin binds local `publishWork(publication)`, `publishContext(contextPointer)` and `deliverContext(delivery)` to the actual host; Broker binds `publishWork`, `getWorkContext` and `designateCoordinator` capabilities behind its existing `handle`, not additional service methods. A publication carries actual SessionKey, optional existing TaskKey, repository/worktree/ref/SHA, declared intent/status, affected resources, blockers/dependency references and revision/freshness. Context carries only consented task-relevant summary/pointers and audience; a delivery receipt distinguishes inbox-persisted from host-queued from demonstrably consumed, leaving unknown explicit. Coordinator designation binds authenticated principal and live session/incarnation, expected prior revision and explicit handoff/expiry policy. These identifiers require final wire/schema review; unavailable native admission remains a prerequisite, never a successful no-op.

For CI/CD linking, extend existing `targetEvidence`/`collectCiEvidence` and `recordLocalEvidence`/`recordReviewEvidence`/`recordDeploymentEvidence` capability contracts only where necessary: exact repository/PR/head/base/integration/run/attempt/checkout identity; immutable artifact and producer provenance; reviewed infra revision, Argo desired/live revision and private acceptance result. The adapter's existing `pollCi` remains observation-only; no proposed `merge`, `deploy` or global-lock method. Validation/authorization/conflict/unknown-outcome failures stay explicit in owning Effect error channels, not log-and-continue success.
